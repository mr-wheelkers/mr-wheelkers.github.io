simq

A queue for iOS simulator tests. Any number of sessions submit a test run; an always-on harness runs them one per simulator, with warm DerivedData, and hands back the result.

How it works

  1. A person, a script or a Claude Code agent submits a run with simq submit --wait.
  2. The broker owns the queue on disk and hands jobs out as leases. It re-queues a job when its worker stops heart-beating and gives up after 3 attempts.
  3. A worker claims the job and builds into a DerivedData directory per project. The build is skipped when the source fingerprint, Xcode build and settings are unchanged since the last build.
  4. The worker runs the tests on its own simulator, with per-test timeouts on, so a hanging test fails instead of hanging the run.
  5. The result comes back: pass and fail counts, failing tests with messages, timings, artifact paths, and an exit code.

The problem

Several sessions on one Mac all want to run the iOS tests. Each one runs a cold xcodebuild build test, waits behind a lock, or fights the others over a simulator.

On the larger app measured in simq's README, build-for-testing with an empty DerivedData took 307 seconds. A fresh checkout pays that every time.

What it does

  • One queue for everyone: clients only talk to the broker, over a Unix socket.
  • One worker per simulator. Parallelism comes from the pool, not from xcodebuild's parallel testing.
  • Build skipping: an unchanged tree goes straight to testing, and a small change rebuilds incrementally.
  • Self-healing: wall-clock timeouts for build and tests, a retry after rebooting the simulator, and booting that escalates from reboot to erase to a fresh clone.
  • Sharding with --shards N: test classes are dealt over several workers and the results merged into one.
  • Results as data: simq submit --wait --json prints the job and the result as JSON.

The edge

Nothing found combines a local queue, a self-healing pool with one worker per simulator, a fingerprint build-skip, sharding and xcresult summaries. Measured on an Apple Silicon MacBook Air with Xcode 26.6:

StepSmall app, 5 testsLarge app, 417 tests
build-for-testing, empty DerivedData9s307s
build-for-testing, warm, nothing changed2s42s; simq skips this entirely
test-without-building, unit bundle only13s40s
test-without-building, everything76s869s

Only simq-* simulators are ever booted, erased, cloned or deleted.

How it compares

simq is being folded into daleq. daleq's iOS plugin reads the same .simq.toml and adds iPad and Apple Watch pools, leases for hands-on work and progress counts. For a new setup, look at daleq first.

Sharding and snapshot mode are documented for simq. Whether daleq's plugin matches them has not been checked here.

When not to use it

  • You want an agent to build, run, debug and drive an app's UI. XcodeBuildMCP is the default choice for that; simq is the part it leaves out, a queue and a simulator pool.
  • You want to tap and type in a simulator. simq runs XCTest; it does not drive UI.
  • One session, one simulator. Plain xcodebuild is enough.
  • Several Macs. Multi-machine is not built in simq.

Install

Not public yet. The repository is private today. These are the commands as they will be once it is public.

/plugin marketplace add mr-wheelkers/simq
/plugin install simq@simq
/simq-setup

/simq-setup covers install, update, doctor and uninstall. Without the plugin, run the installer in a checkout:

scripts/install.sh                 # or: scripts/install.sh --workers 3 --model "iPhone 17" --runtime 26.5

The first start takes a few minutes: the workers create simq-golden, boot it once, and clone simq-1…N from it.

Quick start

Exit codes of submit --wait: 0 passed, 1 tests failed, 2 build failed, 3 timeout, 4 infrastructure error, 5 cancelled, 64 usage.
