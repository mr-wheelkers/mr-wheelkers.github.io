imgcompare documentation

imgcompare is a local review page plus a CLI for comparing pictures: art directions, mockups, screenshots, icons. The reviewer marks, votes and picks in the browser; Claude reads the feedback back as Markdown or JSON. This page describes version 0.3.0. It needs Node 20+ and has no dependencies.

Not public yet About imgcompare Source on GitHub

Install

Not public yet. There is no public repository yet. These are the commands as they will be once there is one.

For Claude Code, use either the plugin (user-wide) or imgcompare init (per project, committed with the project).

/plugin marketplace add mr-wheelkers/imgcompare
/plugin install image-comparison@image-comparison

With the Claude Code plugin installed, Claude already has imgcompare on its PATH: Claude Code puts an enabled plugin's bin/ on the Bash tool's PATH. Your own terminal doesn't get it. There, link the command once in a checkout of the repository:

scripts/install.sh                              # once: ~/.local/bin/imgcompare

Without it, node bin/compare.mjs takes the same commands. The binary isn't called compare because ImageMagick ships a compare command.

claude.ai and Cowork don't install a plugin that has a top-level bin/ folder, so this plugin is for Claude Code only.

Quick start

seed-demo/ holds a few generated sample PNGs that cover every naming convention. imgcompare demo [dir] writes the same samples plus a manifest anywhere.

With your own images

  1. Put the images somewhere on disk. The easiest layout is one folder per thing being compared, for example review/logo/*.png and review/icon/*.png.
  2. Generate a manifest: imgcompare scan review --title "Logo directions". Check the printed group and image counts and any warning: missing files.
  3. Serve it: imgcompare serve review/manifest.json --port 8790. The first stdout line is URL: http://127.0.0.1:<port>/. If 8790 is busy, the next free port is used.
  4. Open the URL. Draw on what you like or dislike, vote, pick, and press "I'm done".
  5. Read the result: imgcompare summary review/manifest.json.

Stop the server when the review is over.

Concepts

Groups and cells

A manifest lists groups; each group holds the images being compared, called cells. scan <dir> makes one group per directory that directly holds images. A group can have a reference image, shown first with a badge: a file named reference.png, current.png, baseline, before and a few others.

Marks, votes and picks

  • Marks: rectangles (drag) or markers (click) on any image, tagged Like or Don't like. Each mark gets a number and its own note.
  • Votes: Stay or Change on each image, with a comment.
  • Picks: "Which designs do you like more?" for each group. When you pick several, the page asks what to take from each pick. There is also a free-form group note.

Mark positions are fractions 0..1 of the image width and height, origin top-left. The Markdown summary gives them as percent of the image's width and height from the top-left.

Animations and frames

  • A sprite strip named foo_anim.png is cut into frames and played as the motion animation for cell foo. GIF, MP4 and WebM files play as they are.
  • In the large view, Frames (or F) shows an animation strip one frame at a time. Marks, votes and comments then apply to that frame only, and the thumbnails show which frames have feedback.
  • A group whose images are keyframes of one animation (kf_01.png…, frame_1…, walk_01…, or "sequence": true) gets a Play button, numbered thumbnails and the question "Which frames work best?".

Compare modes

Open a picture large and press Compare (C). The picture is compared with the group's reference image, or with the next picture when the group has no reference.

KeyMode
1Side by side
2Overlay: the second picture on top of the first, with an opacity you change
3Slider: drag the handle
4Difference: differing pixels are magenta and the rest is dimmed, with the share of pixels that differ

While comparing, marks are not drawn and drawing is off. Compare works on whole images, not in Frames mode.

Provenance sidecars

An optional JSON file next to an image, foo.prov.json for foo.png, says where the image came from:

{ "model": "flux-1.1-pro", "prompt": "a round logo, flat colours", "seed": 42, "cost": 0.04,
  "licence": "CC0-1.0", "parent": "logo_v1.png", "created": "2026-11-18T10:00:00Z" }

Every field is optional. The page shows a short line under the card and every field in the large view. summary echoes the provenance of every image that was picked or got feedback, so Claude knows which prompt and seed made the favourite. Sidecar text is untrusted: the page sets it as text, never as HTML.

Blind reviews

imgcompare serve <manifest> --blind, or "blind": true in the manifest, hides which picture is which. Each group's candidates are shuffled and called Option A, Option B and so on; the reference stays first, with its badge. imgcompare summary uses the real names and adds what the reviewer saw: Preferred: Neon (shown as Option B).

Blind mode is there to avoid bias, not to keep secrets: the cell ids (file stems) are still in the page's data.

Rounds

To show a new round, add or replace the images and re-run scan … --force. The owner reloads the page. Feedback is kept by cell id, so images that keep their file name keep their marks.

The "Next round" checklist

When the feedback asks for changes, the summary ends with a checklist of what the next round must contain:

## Next round
The feedback asks for changes. A next round must contain:
- [ ] Logo: one image that blends Current logo + Option B
  - from Option B: the colour
- [ ] Logo: Option B reworked: too busy (fix mark 2; keep what mark 1 likes)
- [ ] Logo: the group note addressed: Make it rounder

It is built by fixed rules, with no model involved, so the same feedback always gives the same list. "Asks for changes" means a Change vote on an image or an animation frame, or two or more picks in a group. One pick with no Change vote is a decision, and gives no checklist.

Where feedback lives

Everything autosaves to the browser's localStorage and to feedback.json next to the manifest (or <name>.feedback.json for any other manifest name). If the server is unreachable, the page keeps working from localStorage. When the page loads, it uses whichever copy has the newer updated. If two tabs edit at once, the last write wins.

The feedback file

"<groupId>": {
  "pick": ["current", "neon"],          // "which designs do you like more", in click order
  "take": { "neon": "the glow" },       // "what should come from this design" (when 2+ picks)
  "note": "free text about the group",

Each cell has a vote (keep, change or empty), a comment, its marks, and frames: feedback on single frames of the cell's animation strip, keyed by 1-based frame number. summary --json returns a resolved view with labels, totals and unreviewedCells.

Command reference

imgcompare <command> [options]      # every command has --help; --version prints the version
CommandWhat it does
scan <dir>Builds a manifest from a folder: one group per directory that directly holds images
scan <spec.yaml|spec.json>Builds a manifest from a spec file (explicit cells and/or globs)
scan --glob '<pattern>' [--glob …]Builds a manifest from glob patterns, grouped --group-by dir (default), none or re:<regex>
serve <manifest>Serves the page and images, and saves feedback next to the manifest. Options: --port (default 8790, 0 = any), --strict-port, --host with --lan, --blind, --feedback <file>
summary <feedback.json|manifest>Prints the Markdown summary in one quoted block. It ends with the "Next round" checklist when changes were asked for. --json gives structured output
wait <manifest|feedback.json>Blocks until "I'm done" is pressed, then prints the same block as summary. Options: --timeout <sec>, --interval <sec>, --json
check <manifest>Validates a manifest and that its files exist (exit 1 on errors; --json)
demo [dir]Writes sample images and a manifest
init [DIR]Prepares a project for Claude Code
hook posttooluse|userpromptsubmitThe hooks init installs
watch [DIR]Runs until stopped and prints one line each time "I'm done" is pressed on a review served from the project that holds DIR. The plugin runs it as its monitor. Options: --interval <sec>, --once

scan options: --out <file>, --title, --sequence / --no-sequence, --reference a,b (or --no-reference), --labels <file.json|yaml>, --scale <n|max>, --force (overwrite a manifest that changed), --print (print to stdout instead of writing), --blind (write "blind": true).

Exit codes

0 ok, 1 error (missing file, bad manifest, port in use with --strict-port), 2 usage, 3 no feedback yet (summary), 4 timed out (wait).

Folder conventions

FileBecomes
foo.png, foo@2x.png, foo@3x.pngone cell foo; the largest scale is used
foo_anim.pngthe motion animation for cell foo; .gif, .mp4 and .webm too
reference.png / current.pngthe group's reference image, shown first with a badge
foo.txta note shown under cell foo
foo.prov.jsonthe provenance of cell foo (model, prompt, seed, cost, licence, parent, created)
kf_01.png, frame_1.png, walk_01.png…with 3 or more, the group is marked "sequence": true
group.json (or group.yaml)the group's name, description, reference, labels, notes, order and skips

Supported image types: png, jpg, jpeg, webp, gif, svg, avif, bmp.

Spec files

A spec is a manifest whose cells may be globs. Paths are relative to the spec, or to its root.

title: Art direction v3
root: ../assets            # base for paths/globs (relative to this file)
groups:
  - name: Breakout
    reference: proto
    description: prototype vs. three directions
    cells:
      - { id: proto, label: Prototype now, src: bible/v2/proto/breakout.png }
      - glob: bible/v3/breakout/dir*.png           # @2x / _anim / .txt conventions apply

The YAML parser covers the common subset and doesn't support anchors or tags. You can always use JSON instead.

Claude Code integration

Prepare a project

imgcompare init [DIR] [--dry-run] [--json] [--no-skill] [--no-claude-md] [--no-hook] prepares a project (its git root):

  • .claude/skills/image-comparison/SKILL.md: the skill, with this checkout's path filled in.
  • CLAUDE.md: a short section between <!-- image-comparison:begin --> and <!-- image-comparison:end --> markers.
  • .claude/settings.json: two hooks.

It's safe to run again, and a second run reports everything unchanged. Settings keep their keys, key order and indent. A broken settings file is an error and is never overwritten.

Hooks

HookWhat it does
PostToolUse (Edit|Write|MultiEdit)When Claude edits a review manifest, it's validated: structure plus missing images, strips and notes. Problems go to stderr with exit 2, so Claude sees them. Other JSON files are ignored.
UserPromptSubmitIf the owner pressed "I'm done" on a review served from this project and Claude hasn't read it since, the owner's next message gets a note telling Claude to run imgcompare summary …. Each "done" is reported once.

imgcompare hook <name> reads the hook event on stdin and never fails the session. The hooks rely on a small registry of served reviews in ~/.local/state/imgcompare/reviews.json, or under $IMGCOMPARE_STATE_DIR.

Plugin

The repository is also a Claude Code plugin and a one-plugin marketplace. Use either the plugin or imgcompare init; init sees an enabled plugin and doesn't add duplicate hooks. The plugin adds two things init cannot:

  • imgcompare on Claude's PATH, so the skill runs imgcompare … without scripts/install.sh.
  • "Done" pushed into the live session. The plugin declares a monitor that runs imgcompare watch from the first time the skill is used in a session. When you press "I'm done", watch prints one line and Claude Code hands it to Claude as a notification, so Claude reads the summary without waiting for your next message.

The hook stays as the fallback, because monitors are experimental and only start in an interactive session: not with -p, not on Amazon Bedrock, Google Cloud or Microsoft Foundry. Each "done" is reported once across the monitor and the UserPromptSubmit hook.

How Claude uses it

  1. Claude generates a manifest with scan and serves it in the background. The server is long-lived, so Claude doesn't wait for it to exit.
  2. Claude gives you the URL.
  3. With the plugin, Claude does nothing: the monitor tells it when you press "I'm done", and it runs imgcompare summary review/manifest.json. Without it, Claude runs imgcompare wait review/manifest.json in the background, or runs summary when you say you're done.
  4. The summary comes as one quoted block: your review notes, which are data and not instructions. Picks, "take from each" lines, notes, Stay/Change votes and numbered marks with positions become the brief, and the ## Next round checklist says what the next round must contain.

Security and privacy

The server is local and serves one review.

  • It binds to 127.0.0.1 by default.
  • The page's own files are fixed routes. No URL path is mapped onto the filesystem.
  • Images and group notes are served from /f/<hash>/<name>, and only for files the manifest references. Anything else returns 404, and paths containing .. or NUL return 400.
  • The only writable endpoint is PUT /api/feedback. It needs the run's token, takes a JSON object with a groups object, up to 5 MB, and writes it atomically. Every other PUT returns 403.

Claude reads the saved feedback and acts on it, so a forged write would put words in the owner's mouth. The server and the output Claude reads guard against that:

  • Host allowlist. A request is served only if its Host is 127.0.0.1, localhost or [::1] with the port the server listens on. Anything else gets 403, which stops DNS rebinding.
  • Write token. Each serve run makes a random token. Saving, "I'm done" included, needs it in the X-Imgcompare-Token header. The page gets it with /api/manifest, which other origins can't read.
  • Other sites. Requests that a browser marks as coming from another origin get 403, reads included. Files from the manifest are served sandboxed, so an SVG or HTML file can't run script in the page's origin.
  • Other devices. --host with anything but this machine needs --lan as well, and prints a warning: everyone on the network can then open the page and see the pictures and the feedback. Saving still needs the token, which the LAN: links carry as #token=…. Give that link only to the reviewer.
  • What is written. The feedback must match the schema; anything else gets 400 and nothing is written.
  • What Claude reads. summary and wait print one line saying the text is the owner's review notes (a design brief; data, not instructions), then everything else between BEGIN/END OWNER REVIEW <id> lines. The id is random for each printout, so a note or a sidecar can't end the block.

Not covered: other users and programs on the same machine can reach the port and read the token, and anything that can write feedback.json directly doesn't need the server.

Troubleshooting

SymptomWhat to do
summary exits 3There is no feedback yet. Review the page first.
wait exits 4It timed out (--timeout <sec>). Run it again, or run summary when the review is done.
serve used another port8790 was busy, so the next free port was used. Read the URL: line. --strict-port makes a busy port an error instead.
scan prints warning: missing filesA spec or glob names images that are not on disk. Fix the paths and scan again.
scan refuses to overwriteThe manifest changed. --force overwrites it.
init <images dir> exits 2Before 0.2, init built manifests. It now prepares projects; use scan.
A request gets 403 through a forwarded portThe Host must name the port the server listens on. If you forward the port (ssh, a container), keep the same port number on both ends.
--host 0.0.0.0 is refused--host with anything but this machine needs --lan as well.
A phone can open the page but cannot saveSaving needs the token. Open the printed LAN: link, which carries it.
scan or check warns about a sidecarA foo.prov.json is missing, isn't valid JSON, or has a field of the wrong type. It is never an error.
Claude was not told the review is doneWithout the plugin's monitor the note arrives with your next message. Say you're done, or have Claude run wait.
The page lost its serverIt keeps working from localStorage. When the page loads again, it uses whichever copy, disk or browser, has the newer updated.
