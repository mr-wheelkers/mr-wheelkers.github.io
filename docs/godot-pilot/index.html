godot-pilot documentation

GodotPilot gives Claude hands and eyes on a Godot 4.7.2 .NET project in development: the running game, the editor, and the project's configuration. It stays out of exported builds. macOS and C# only. Jev (TypeSafe AI) is its optional, paid fast eyes and classifier.

Not public yet About godot-pilot Source on GitHub

Install

Not public yet. The repository is private today, so there is nothing to check out yet. This is how it will work once it is public.

What you need

  • macOS. It is built and verified on an Apple Silicon Mac; Windows and Linux are the design target, not yet verified.
  • Godot 4.7.2 .NET. The harness is C# and needs a .NET game assembly, so GDScript projects are out of scope.
  • netcoredbg, only for breakpoints (pilot debug).
  • Optional: a TYPESAFE_API_KEY in the environment for Jev. Jev is paid.

Adopt it in a project

There is no packaged installer or plugin yet. The pilot CLI is run from a checkout of the repository, and another Godot .NET project adopts it with pilot init:

pilot init --project <dir>

It links the addon, adds a csproj block against prebuilt assemblies, sets the export filter, and writes .gitignore lines and .pilot/config.json when missing. The steps print one line each, then pilot doctor runs. Add --also <logic.csproj> for a plain-logic assembly.

  • Afterwards git status of the project shows only the csproj block, the export filters, .gitignore and .pilot/config.json.
  • A second init changes nothing. Re-run it after any protocol or analyzer change; pilot doctor says when.
  • pilot init --remove takes it all out again.
  • Before any export, run scripts/release-gate.sh --project <dir/game>.

Quick start

Drive a running game

Success prints nothing unless the command's purpose is output: get prints the value as JSON, and shot prints the PNG path and its sha256.

Run a scenario

pilot scenario run demo/scenarios/<name>.json

The CLI launches the game with the standard line, loads the fixture, executes the steps and stops the game. Success is exit 0 and no output. A failure is non-zero and at most 10 lines naming the failed step and the bundle path.

Edit in the editor, verify in the played game

Concepts

Tiers: push every bug to the cheapest one that catches it

TierTimeWhatCatches
0<1sRoslyn analyzers, xUnit on pure logicrules, math, state machines, wiring
1secondsGdUnit4 headless, no renderingscene, physics, signal logic
2~10srendered scenario run via harness, frame-steppedintegration, UI, visuals
3minutesexploratory Jev-watched runsstuck states, soft-locks, oddities

A bug found in tier 2 or 3 gets a tier 0 or 1 reproduction test before the fix. Game logic lives in plain .NET classes, not Node subclasses; nodes are thin adapters.

Verification order

  1. Engine or editor state (harness get/eval, editor read-back). If it answers the question, ask nothing else.
  2. Jev, only for what state cannot answer ("is a dialog open", "does this look broken").

Determinism

Runs use a fixed timestep (--fixed-fps 60), a seeded RNG and an injectable clock. A flaky test is a bug. A frame hash is only deterministic under frame stepping and on the same renderer, GPU/driver and resolution: hashes taken on one machine are not expected to hold on another.

Fixtures, scenarios and recordings

A fixture is a scene plus state, applied after the scene's _Ready and before its first tick. Reaching a state is always a fixture, never a click-through. A scenario is a JSON file of steps; each scenario runs in a fresh game process.

Step opWhat it does
loadload a scene, optionally with a fixture, seed and clock
inputclick, move, drag, scroll, key, text or action
stepadvance N frames; expectSha asserts the frame hash
setset a state value and read it back
waitpoll until a value equals, a node is visible or the tree changed, within a frame budget
assertdeep JSON equality on a value, a regex on a string, or a node visible or hidden
shottake a screenshot; expectSha asserts its sha256
jeva Jev check; with Jev off the step is skipped
checkpointhash a list of state paths; a mismatch on replay is a desync
evalrun C# and optionally compare the result

pilot scenario record starts a run in record mode: every input and step the CLI sends is appended to a scenario file, with a checkpoint step every 60 game frames. pilot scenario replay runs it and reports the first checkpoint mismatch. Recording covers CLI-driven input only, not human play.

Runs

Each run has a folder, .pilot/runs/<run-id>/, with a manifest, a trace, shots, logs and, on failure, a bundle: the shot at the failed step, the tree, the tree diff against the previous step, logs, and inputs since the last checkpoint. A passing run keeps only the manifest and trace by default.

Two runs in one project dir are not supported, by design. Each run writes the project's override.cfg, and the CLI refuses a second one. An editor session is not a run and coexists with one.

Background launches and "verified"

On macOS every game launch and pilot editor open start Godot in the background by default, so they do not take your keyboard focus. --focus opts out. A result from a background run never counts as tested on its own: scenario run marks it verified: false, and a foreground run confirms it.

The editor

pilot editor drives a Godot editor through the editor harness: UI tree, input, editor API calls, live eval and editor logs. Editor work is not deterministic and is not a tier; every command that acts reads its effect back before it reports success.

A violation fails dotnet build -warnaserror. Fix findings rather than suppress them; [GodotPilot.AllowNondeterminism] marks the clock and RNG adapters that may read the system.

Debugger and housekeeping

pilot debug attach, pilot debug bp <file>:<line>, pilot debug continue, pilot debug bt, pilot debug locals and pilot debug detach drive netcoredbg. The debugger is frozen: kept working, no new work.

pilot clean <run-id>, pilot clean --older-than <age> and pilot clean --all delete runs. pilot config [--json] prints the effective configuration with sources.

Exit codes

CodeMeaning
0ok
1a check failed: assert, replay desync, wait timeout, scenario step failure
2usage or config error (unknown command, bad flag, invalid scenario file, missing fixture)
3harness unreachable: launch failed, connect or request timeout, protocol error, game exited
4budget exceeded (Jev $ or request cap)
5escalation: Jev uncertain or not found, or a failure that produced a bundle for Claude
6skipped: the command needed Jev and Jev is disabled; never a pass

Configuration

Precedence: built-in defaults, then .pilot/config.json (repo root, committed), then environment GODOT_PILOT_<SECTION>_<KEY>, then flags. Secrets come only from the environment (TYPESAFE_API_KEY).

Claude Code integration

Claude Code uses GodotPilot through the pilot CLI in its shell. There is no MCP server: the CLI is the one interface. The contract is written for an agent:

  • Failures and diffs only. Success prints nothing unless the command's purpose is output. Full logs come on request with --verbose.
  • Every command that acts verifies through engine state before it reports success.
  • Every engine invocation is bounded: a timeout on the process, and --quit-after as a last resort.
  • One bundle on failure: screenshot, Jev scores, scene-tree diff, recent logs.
  • Exit codes carry the outcome, so an agent can branch without parsing prose.

Roles

  • Claude: plan, code, test design, debugging, triage of escalations. The driver.
  • The harnesses: deterministic execution in the game; a free-running executor in the editor.
  • Jev, when enabled: fast eyes and classifier. It never acts on its own.
  • You: feel, priorities, anything subjective.

Analyzers in the build

The analyzers run at tier 0, in dotnet build, so the agent meets a Godot pitfall as a build error with a rule id rather than as a bug at run time. pilot init wires the prebuilt analyzer assembly into the project's csproj.

Security and privacy

What leaves the machine

Only screenshots of seeded game content, sent to Jev, and only when Jev is enabled. The game harness marks seeded frames seeded=true, only in a project whose .pilot/config.json sets harness.seededContent; the Jev client refuses any image without the marker. Editor screenshots never carry it, so they cannot be sent. No source code, logs, state dumps, settings or editor content is sent to Jev.

GodotPilot treats anything sent to Jev as retained indefinitely, which is why only seeded content is sent. Data already sent to Jev cannot be deleted by GodotPilot.

Jev is optional and paid

With jev.enabled=false or no TYPESAFE_API_KEY, Jev commands and jev scenario steps report skipped: Jev disabled and exit 6; they never pass. A run has a spending cap and a request cap (budgetUsd, requestCap in the configuration). TYPESAFE_API_KEY comes only from the environment: never logged, never in a run dir, never passed to a child process.

Local access

  • Harness ports are bound to localhost only, with a per-session token. Tokens are per-run random values in 0600 files.
  • pilot eval and pilot editor eval run C# inside the running game and the editor. That is the point of the tool, and it is as powerful as it sounds.
  • There is no sandbox. Claude Code, builds, NuGet packages, the game and the editor run as your own user.

Nothing ships

The harness compiles only under GODOT_PILOT, editor-side code also sits inside #if TOOLS, and neither the autoload nor the plugin is ever in a committed project.godot. The harness run settings live in .pilot/config.json and are written per run into override.cfg, which an export does not carry. The release gate proves it, for any project.

What is stored locally

.pilot/runs/<run-id>/, the Jev cache .pilot/jev-cache/, and .pilot/editor/<id>/ for editor sessions. They are kept until deleted. pilot clean does not touch .pilot/editor/ yet: delete those directories by hand.

Troubleshooting

SymptomWhat to do
Exit 3The harness is unreachable: the launch failed, a connect or request timed out, or the game exited. Start a new run.
Exit 2 naming an override.cfgAnother run owns this project dir. pilot stop --run <id> first, or use another project dir.
WARN scenario run unverified (background only)Every run launched in the background. A foreground run (--focus or GODOT_PILOT_LAUNCH_TAKEFOCUS=1) confirms them.
eval hung the game; restart itThe eval watchdog ended the game. Start a new run.
restart the game before the next evalAn eval timed out in this game; every later eval is refused until a restart.
Exit 6, skipped: Jev disabledThe command needed Jev. Enable it, or pass --allow-skip where it is offered.
shot is unavailableHeadless (--headless) runs have no pixels.
no editor session: start one with pilot editor openEditor commands act on an open session. Run pilot editor open first.
pilot editor close exits 1Scenes are unsaved; it names them. Save, or pass --save.
CS8032 or CS9057 in the build outputThe analyzers did not load.
After any settings or plugin changeRun pilot doctor. Each finding is one line naming the file and the key.
