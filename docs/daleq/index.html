daleq documentation

daleq is a small local daemon that runs long commands for a coding agent: it hands back a job id at once, runs the command under watchdogs, and keeps every output and outcome on disk. Supported on macOS and Linux; Windows is experimental.

Not public yet About daleq Source on GitHub

Install

Not public yet. The repository is private today. These are the commands as they will be once it is public.

As a Claude Code plugin:

/plugin marketplace add mr-wheelkers/daleq
/plugin install daleq@daleq
/daleq-setup

/daleq-setup downloads the prebuilt daleq binary for your machine from the latest GitHub release, checks it against the release's checksums and installs it to ~/.local/bin. Then restart Claude Code so the MCP server starts.

The plugin brings the MCP server (daleq mcp), the hook (daleq hook pretooluse), the daleq skill and /daleq-status.

Without the plugin

Install the binary yourself and add the MCP server:

claude mcp add daleq -- daleq mcp
  • Prebuilt, on macOS and Linux: scripts/install-release.sh [TAG]. PREFIX=… changes where it goes.
  • On Windows: download daleq_windows_amd64.exe or daleq_windows_arm64.exe from the releases, rename it to daleq.exe and put it on PATH.
  • From source (Go 1.22+): scripts/install.sh.

Re-run either script to update. Both stop the daemon (daleq stop) so that the next call starts one on the new binary; running jobs are unaffected.

What the release installer checks

  • Integrity, always: the binary must match its line in the release's SHA256SUMS. That file comes from the same release, so this catches a damaged download, not a tampered release.
  • Provenance, when gh is installed and signed in: gh attestation verify checks GitHub's build provenance attestation for that exact binary. A binary without one is refused, except with DALEQ_ALLOW_UNATTESTED=1. Without gh only the checksum is checked, and the script says so.

Provenance shows the binary was built by daleq's CI from the repository. It does not vouch for the code itself.

Check and uninstall

daleq version prints the version and the build. daleq doctor checks the install: binary on PATH, daemon running and the same build, Claude Code hook and MCP server registered, jobs and pools.

To uninstall:

  1. /plugin uninstall daleq@daleq (or claude mcp remove daleq without the plugin).
  2. daleq service uninstall, if you installed the always-on service.
  3. Delete ~/.local/bin/daleq and daleq's home (see Security and privacy).

Quick start

Ask the agent in plain words. The skill and the hook steer it to daleq.

  • "Run the full test suite and tell me what failed."
  • "Start the dev server and check the home page loads."
  • "Build the release, I'll be back in an hour."

Prepare a project

daleq init, in a project's folder, prepares it so that everyone who opens it in Claude Code uses daleq. It writes:

  • .daleq.toml, when there is none: the project's build and test commands as tasks. An existing one is never rewritten.
  • CLAUDE.md (or .claude/CLAUDE.md): a short daleq section between <!-- daleq:begin --> and <!-- daleq:end -->. A rerun replaces only that section.
  • .gitignore: .daleq.local.toml, this machine's own settings.
  • .claude/settings.json: the daleq plugin enabled for the project. With --no-plugin, init writes the hook, the skill and .mcp.json into the project instead.

Running init again changes nothing. --dry-run shows what it would change, and --json prints the same as data.

From a shell

Jobs run in the daemon's environment, not your shell's. Pass what a job needs with --env X=1, or --pass-env X.

Concepts

Daemon and supervisor

The daemon queues jobs, schedules them and answers clients over a unix socket (daleq.sock in daleq's home). The first client call starts the daemon if it isn't running.

A supervisor per job owns the command. It runs detached, so restarting or crashing the daemon never kills a job. Everything about the job lives in jobs/<id>/: job.json, status.json, output.log. A job whose supervisor vanished without an outcome becomes orphaned, and its leftover processes are killed.

States

queued, running, ready (ready_on matched, still running), succeeded, failed, timed_out, idle_killed (no output for the idle timeout), cancelled and orphaned (its supervisor died; rerun).

Watchdogs

  • Wall clock: default 30 min (timeout_sec, --timeout), capped at 6 h (max_timeout_sec). A ready server is stopped at its wall clock too.
  • Idle output: no output for 10 min means hung.
  • fail_on: an output regex that ends the job as failed.
  • ready_on: an output regex that marks a server ready and keeps it running.
  • Check-ins, for servers: a ready_on job submitted without a timeout is not stopped by a 30-minute clock. After an hour, daleq asks the submitting session whether it is still needed; daleq keep ID keeps it for another hour.

Kills go to the whole process group: SIGTERM, then SIGKILL after 5 s.

Pools and scheduling

  • cpu jobs share a weight budget (default: core count). A full build might be weight 4, lint 1.
  • io jobs (downloads, servers, polling) take one of 32 slots.
  • Higher priority runs first, and queued jobs gain one point per 5 minutes, so nothing starves.
  • Named locks (exclusive or shared) keep, for example, two npm installs out of the same node_modules.

Result reuse

The key defaults to cmd + cwd + env, and is matched together with a fingerprint of the git tree (HEAD + diff + untracked files) plus the contents of the files the command names as inputs. Resubmitting attaches to a job that is still running, or that succeeded on the same tree in the last 24 h. If anything changed, the command runs again.

Failures always rerun, and so do finished servers (ready_on) and io jobs without --output. Use --key for your own keys, --key - to opt out, and --force to rerun.

Bounded waits

A server-side wait blocks at most 120 s. daleq submit --wait and daleq wait block at most --max-wait: default 540 s, under an agent's 10-minute shell timeout. They exit 6 if the job is still running.

Pipelines fail when any part fails

Commands run under sh -o pipefail where /bin/sh supports it, else under bash -o pipefail, so go test ./... 2>&1 | tail -30 fails when go test does. A reader that quits early (| head, | grep -q) can then fail the job with exit 141. --no-pipefail restores plain sh.

When a job succeeds but its tail has a failure line, the MCP result carries a warning. When one fails, it carries highlights: the first such lines above the tail, up to 10, so the first error shows even under a long stack trace.

Project settings and tasks

A .daleq.toml at the root of a repository gives every job submitted there the same environment and starting options, and names the commands the project runs:

[requires]          # checked before a job starts; a bare version is that line ("3.12" = any 3.12.x)
go = ">=1.22"

[tasks.test]
cmd = "go test ./..."
description = "unit tests"
weight = 4
timeout = 1200
fail_on = "^panic: "

[tasks.serve]
cmd = "npm run dev"
dir = "web"         # relative to the checkout's root
kind = "io"
ready_on = "ready in"

daleq tasks lists them, and daleq run test -- -run TestFoo runs one and waits. .daleq.local.toml (gitignore it) overrides the file for one machine. daleq checks tools; it never installs them.

Keeping the machine awake

While daleq has a build, test or other job that ends by itself, it asks the OS not to idle-sleep, so a laptop left alone finishes the work. The display may still turn off, and closing the lid still sleeps the machine. Dev servers and io jobs without outputs don't count; --keep-awake makes one count.

Device pools and leases

Plugins add job types and resource pools, all compiled into the one binary. The iOS plugin has pools of iPhone (sim), iPad (ipad) and Apple Watch (watch) simulators that share one limit, max_devices (default 3). The shell plugin turns any list of devices into a pool, with an optional heal command.

cd MyApp && daleq submit --plugin ios --args '{"kind":"unit"}' --wait   # 0 passed, 1 failed, 2 build failed, 3 timeout, 4 infra
daleq submit --resource watch -- ./sim.sh test                          # any command, with a booted watch simulator
daleq lease sim --note "login screen screenshots"   # prints the lease id and DALEQ_SLOT_SIM=simq-2
daleq release lease-3f9a1c2e                        # the slot is healed before anyone else gets it

A lease is meant to be held only while it is used. After --ttl (120 s) without a call, a queued job that needs the pool may reclaim it; after --lapse (900 s) it ends anyway; and it ends after --max (2 h) however often it is renewed. Slots left in a bad state are healed before anyone reuses them.

Several machines

One queue can span several machines, connected over any network where they can reach each other: a LAN, Tailscale or WireGuard. One machine coordinates; every machine, the coordinator included, runs jobs as a node. In a cluster, a job submitted from a git work tree carries a snapshot of it, so any node can run it.

daleq cluster init --advertise mac.local        # on the coordinator: prints a one-time join command
daleq cluster join mac.local:7787 TOKEN --ca FP # on each other machine
daleq cluster status                            # role, coordinator, nodes and what each has

Command reference

daleq submit [flags] -- CMD...      # prints the id; --wait / --until-ready to block (bounded)
    --kind cpu|io  --weight N  --priority N  --key K  --force
    --timeout SEC  --idle-timeout SEC  --fail-on RE  --ready-on RE
    --lock NAME[:shared]  --resource POOL[:N]  --env K=V  --cwd DIR  --label TEXT  --max-wait SEC  --json
daleq status [REF] [--json]          # REF = id, key, or a unique part of an id
daleq list [--all] [--limit N] [--label TEXT]   # --label: jobs whose label contains TEXT
daleq wait REF [--max-wait SEC] [--until-ready] [-q]
daleq logs REF [--tail N | --offset N] [--follow]   # --grep RE: only matching lines, as OFFSET: line
daleq cancel REF
daleq top [--once] [--every SEC] [--recent N]   # live panel: nodes, running/queued jobs, pools, recent outcomes
daleq lease POOL [--wait SEC]        # take a device for yourself (below); daleq release ID gives it back
daleq prune
daleq service install|uninstall|status   # optional: keep the daemon always on (launchd agent / systemd user unit)

One argument after -- is a shell command ('make test | tail'). Several arguments are a program and its arguments, not shell syntax: daleq quotes each one for the shell that will run the job.

Exit codes

0 succeeded, 1 failed, 3 timed out / idle-killed, 4 orphaned or daemon unreachable, 5 cancelled, 6 still running, 64 refused (a bad request, or a Claude Code deny rule). daleq lease exits 75 when no slot frees up within --wait.

Configuration

Configuration lives in config.json in daleq's home. Every key is optional: cpu_budget, io_slots, aging_minutes, starvation_minutes, max_timeout_sec, reuse_hours, retain_days, max_log_mb, lease_sec, plugins and more. Environment: DALEQ_HOME, DALEQ_SOCKET, DALEQ_MAX_WAIT, DALEQ_HOOK, DALEQ_VOICE=plain.

Claude Code integration

The plugin

The plugin brings four things: the MCP server (daleq mcp), the hook (daleq hook pretooluse), the daleq skill that tells the agent when and how to use it, and /daleq-status. /daleq-setup installs the binary.

The hook

The hook turns away Bash and PowerShell commands that never end or only wait: dev servers, tail -f and logs -f, watch modes, sleeps of a minute or more, polling loops. It points the agent to daleq instead.

  • It looks only at code. Quoted strings, heredoc bodies and comments are text, so a commit message that mentions sleep 5 or --watch passes.
  • The bodies of bash -c '…', sh -c "…" and powershell -Command '…' are code and are checked.
  • sudo, env, VAR=value, nohup, npx and subshell parentheses in front of a command do not hide it; timeout N in front lets it through when N is under a minute.
  • --help and --version always pass, and so do docker compose up -d and up --wait.
  • To run one command directly, add # daleq:allow to it. DALEQ_HOOK=off turns the hook off everywhere. DALEQ_HOOK=strict also sends every background Bash or PowerShell run to daleq.

The skill

The skill tells the agent not to run in Bash anything that may take more than a minute, never ends on its own, or waits for something, and not to use Bash run_in_background for them either. It teaches the submit, wait, logs and cancel loop, and how to choose options:

SituationOptions
Build or test suitekind: cpu, weight 2–4 for heavy builds, 1 for lint/unit tests
Download, install, API pollingkind: io
Dev server, emulatorkind: io, ready_on, then daleq_wait with until_ready: true; daleq_cancel when done
Fail fast on a known fatal linefail_on: "FATAL|npm ERR!|error: linker"
Legitimately silent for longidle_timeout_sec: 1800 (0 = off)
Two jobs must not touch the same thinglocks: [{"name": "repo/node_modules"}]

After a pause or in a new session

The agent resubmits the same command. If it is still running, or succeeded and the source tree is unchanged, daleq attaches to that job ("attached": true) instead of running it again. force: true reruns a success on purpose.

Security and privacy

What it stores

daleq keeps its state in its home: ~/Library/Application Support/daleq (macOS), $XDG_STATE_HOME/daleq or ~/.local/state/daleq (Linux), %USERPROFILE%\.daleq (Windows), or $DALEQ_HOME. Each job's command, working directory, environment variables passed to it, output and outcome are stored there, readable only by you, and pruned 7 days after the job finishes (retain_days).

daleq itself has no telemetry and makes no network connections, except between machines you join into a cluster yourself.

Project environment values are stored with each job, so keep secrets out of .daleq.toml and use --pass-env for those.

Permissions

Commands sent through daleq are not checked by Claude Code's Bash permission rules or its Bash sandbox: to Claude Code they are an argument of the daleq_submit tool.

  • Claude Code asks before each daleq_submit, showing the command, until you always-allow the tool. The plugin never allows it for you. Keep it on "ask" if you want to approve every job.
  • daleq refuses any job whose command or notify command matches one of your Claude Code Bash(…) deny rules, before it reaches the daemon. Allow and ask rules, the sandbox and commands hidden in scripts are not covered.

What a repository may not set

The committed .daleq.toml may not set variables that change which code a command runs, because then the repository, not the command you approved, would decide what every job does. Refused: program lookup (PATH, SHELL), the dynamic loader (LD_*, DYLD_*), hooks that run commands (BASH_ENV, EDITOR, all GIT_*), configuration directories (HOME, XDG_CONFIG_HOME) and runtime options (every *_OPTIONS and *_OPTS, PYTHONPATH, GOFLAGS). Such a name stops the submit with an error naming it.

The socket

The socket is daleq.sock in daleq's home, or $DALEQ_SOCKET. When daleq has to put it in a short directory instead, clients refuse to connect when that directory is not yours, is a symlink, or is open to others.

Clusters

cluster init creates a small certificate authority. A join token works once, and from then on every call is mutual TLS (TLS 1.3). Nothing is installed or opened beyond the coordinator's listening port (--listen, default :7787). The machines of a cluster trust each other: any of them can submit, cancel and read any job.

Troubleshooting

SymptomWhat to do
No daleq tools in Claude Code; /mcp shows the daleq server as failed, often as CONNECTION_CLOSEDdaleq is not on PATH, or Claude Code started before it was installed. Run /daleq-setup, make sure ~/.local/bin is on PATH, and restart Claude Code.
The hook blocks a command you want to run directlyAdd # daleq:allow to that command, or set DALEQ_HOOK=off.
A job was killed after 10 silent minutes and its log is emptyThe command redirected its output to a file (> out.log 2>&1), so daleq saw nothing. Don't redirect; for a job that is silent for good reason, raise --idle-timeout.
A pipeline fails with exit 141A reader quit early (| head, | grep -q). Drop the pipe: the result has the last 30 lines and daleq logs has --grep.
daleq wait exits 6The job is still running. Run it again.
A submit is refused with exit 64A bad request, or the command matches a Claude Code deny rule. Do not rephrase it to get past the rule.
A job runs in the wrong treeOver MCP, always pass cwd: without it the job runs where the daleq MCP server started, which in a worktree is another tree.
Bash syntax fails on WindowsThe default shell is cmd.exe. Pass --shell bash (Git for Windows' bash, with pipefail) or write the command for cmd.
Anything elsedaleq doctor names what is wrong. The daemon's log is daemon.log in daleq's home, and each job's supervisor log is jobs/<id>/supervisor.log.
