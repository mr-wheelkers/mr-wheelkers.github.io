godot-pilot

A deterministic test and debug harness that lets Claude drive a Godot .NET game and the Godot editor frame by frame, and proves none of it ships. macOS and C# only.

How it works

  1. Claude runs a pilot command, for example pilot scenario run demo/scenarios/<name>.json.
  2. The CLI builds and launches the game and connects to the harness inside it. Harness ports are bound to localhost only, with a per-session token.
  3. The game advances only when stepped. A scenario loads a fixture, sends input, steps N frames, asserts state and takes shots, with a fixed timestep, a seeded RNG and an injectable clock.
  4. Success is exit 0 and no output. A failure is at most 10 lines naming the failed step and the bundle path, under .pilot/runs/<run-id>/.
  5. Optional: Jev answers what engine state cannot, such as "is a dialog open". Only screenshots of seeded game content leave the machine.

The problem

An agent that writes a game cannot see it run. Playing through menus to reach a state is slow. A free-running game gives a different result each time, so a failure cannot be repeated. And a test harness left in the project can ship to players.

What it does

  • Drives the running game: input (including scroll and window resize), frame stepping, screenshots, state get and set, and live C# eval with pilot eval.
  • A testbed: fixtures (a scene plus serialized state), scenarios, record and replay with checkpoint hashes, and exploratory runs that look for soft-locks.
  • Drives the editor with pilot editor: UI tree, input, scene open and save, node properties, live eval, and playing the game from the editor with the harness attached.
  • Reads and changes any setting with pilot settings, adds and removes plugins with pilot plugin, and runs sanity checks with pilot doctor.
  • Checks and renders shaders with pilot shader.
  • Nine Roslyn analyzers for Godot pitfalls, from string GetNode paths (GP0001) to wall-clock time and unseeded randomness (GP0013).
  • Breakpoints in C# through netcoredbg with pilot debug.

The edge

  1. A determinism contract across the stack. Fixed timestep, seed and injectable clock, checkpoint hashes with desync reports, a gate that runs every scenario twice, and an analyzer that fails the build on wall-clock time or unseeded randomness.
  2. Proof that nothing ships. The harness compiles only under GODOT_PILOT, editor-side code also sits inside #if TOOLS, and a release gate proves it for any project.
  3. C# all the way. Live C# eval in the running game and in the editor, netcoredbg breakpoints, and analyzers written for Godot's C# API.
  4. Output made for an agent. Failures and diffs only, one failure bundle, a reversible pilot init, and launches that do not take keyboard focus on macOS.

How it compares

"AI drives Godot" is a crowded field: at least 15 servers were found, and input, screenshots, UI trees and record and replay are free or cheap elsewhere. As a general Godot MCP alternative godot-pilot is redundant. It is different as a deterministic test and debug harness for Godot .NET, which is a niche inside a niche.

When not to use it

  • Your project is in GDScript. The harness is C# and needs a .NET game assembly.
  • You are on Windows or Linux. They are designed for, not verified.
  • You are on another Godot version. It is built and pinned to Godot 4.7.2 .NET.
  • You want an MCP server. There is none: the pilot CLI is the one interface.
  • You mainly want the agent to author scenes in the editor. godot-ai has far more authoring tools.
  • You need gamepad, touch or trackpad gestures. They are still to do; Beckett has gamepad and touch.
  • You need a sandbox. Builds, the game and the editor run as your own user.

Jev is one optional vendor. Without it, Jev steps report skipped (exit 6), never a pass.

Install

Not public yet. The repository is private today, so there is nothing to check out yet. This is how it will work once it is public.

There is no packaged installer or plugin yet. pilot is run from a checkout of the repository, and another Godot .NET project adopts it with pilot init.

pilot init --project <dir>

The steps print one line each, then pilot doctor runs. Afterwards git status of the project shows only the csproj block, the export filters, .gitignore and .pilot/config.json. A second init changes nothing, and pilot init --remove takes it all out again.

Before any export, run scripts/release-gate.sh --project <dir/game>.
