imgcompare

A local review page plus a CLI for comparing pictures: art directions, mockups, screenshots, icons. You mark what you like, pick and blend; Claude reads it back as a brief.

How it works

  1. Claude puts the images on disk and builds a manifest: imgcompare scan review --title "Logo directions".
  2. It serves the page with imgcompare serve review/manifest.json --port 8790 and gives you the URL.
  3. You draw Like and Don't like marks, vote Stay or Change, pick the designs you like more and say what to take from each.
  4. You press "I'm done". Everything is already saved in feedback.json next to the manifest.
  5. With the plugin, a monitor tells Claude at once, and Claude runs imgcompare summary review/manifest.json. Without it, Claude hears with your next message.
  6. The summary ends with a ## Next round checklist when you asked for changes. Claude replaces the images and re-runs scan … --force; images that keep their file name keep their marks.

The problem

An agent makes five logo directions. Your answer comes back as a chat message: the second one, but with the glow from the fourth, and that corner is wrong. Which corner?

For animation it is worse. "The arm pops in frame 3" has nowhere to go when the review is a GIF and a text box.

What it does

  • Draw rectangles (drag) or markers (click) on any image, tagged Like or Don't like. Each mark gets a number and its own note.
  • Vote Stay or Change on each image and leave a comment.
  • Answer "Which designs do you like more?" for each group. When you pick several, the page asks what to take from each pick: a blend.
  • Compare two pictures in the large view: side by side, overlay with opacity, a draggable slider, or a pixel difference.
  • Step through animations frame by frame. Marks, votes and comments then apply to that frame only.
  • See each picture's provenance (model, prompt, seed, cost, licence) when it has a foo.prov.json sidecar.
  • Review blind with serve --blind: shuffled candidates without names, next to the reference.
  • Everything autosaves to feedback.json. Claude reads it back as Markdown or as JSON with --json, with a checklist of what the next round must contain.

The edge

  1. Feedback on a single frame. Marks and votes on one frame of a strip or keyframe sequence, returned to the agent. No other tool found returns this.
  2. Like and Don't like marks, plus what to take from each pick. The output is a brief for the next round, and its checklist is built by fixed rules, with no model involved.
  3. Any images already on disk. One scan, no dependencies, localhost; the files stay in the repository.
  4. Rounds that keep their marks. Feedback is kept by cell id, so images that keep their file name keep their marks.
  5. The owner's words are fenced. Claude reads the review between BEGIN/END OWNER REVIEW <id> lines, as data and not instructions, and saving needs a token made for each run.

How it compares

Showing variants, picking one and leaving a comment is a commodity. imgcompare exists for sprite and animation review, and for turning likes and dislikes into a brief. It is a small tool, not a product.

When not to use it

  • You want visual regression in CI: stored baselines and a build that fails. imgcompare compares two pictures for a person to judge. Chromatic, Percy, Argos and reg-cli do regression.
  • You want the user to choose between two to four text options. Claude Code's AskUserQuestion needs no install.
  • The designs were made in Claude Design. Review them there.
  • You need pixel-exact regions. Mark positions are percentages of the image, and Claude has to find the region from them.
  • You want several reviewers with accounts. There are none. With --host 0.0.0.0 --lan, everyone on the network can open the page and see the pictures and the feedback; saving still needs the token.
  • You use claude.ai or Cowork. They don't install a plugin that has a top-level bin/ folder, so this plugin is for Claude Code only.

The "done" monitor depends on Claude Code monitors, which are experimental and only start in an interactive session. The UserPromptSubmit hook stays as the fallback.

Install

Not public yet. There is no public repository yet. These are the commands as they will be once there is one.

As a Claude Code plugin, user-wide:

/plugin marketplace add mr-wheelkers/imgcompare
/plugin install image-comparison@image-comparison

With the plugin installed, Claude already has imgcompare on its PATH. Your own terminal doesn't get it: run scripts/install.sh once in a checkout, which links ~/.local/bin/imgcompare.

Or per project, committed with the project: imgcompare init. Use either the plugin or init; init sees an enabled plugin and doesn't add duplicate hooks. With init alone there is no monitor.

Quick start

seed-demo/ holds a few generated sample PNGs that cover every naming convention. imgcompare demo [dir] writes the same samples plus a manifest anywhere.
