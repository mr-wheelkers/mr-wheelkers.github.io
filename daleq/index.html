daleq

A job daemon for coding agents: every long command gets a watchdog and a durable result, and is never run twice on the same tree.

How it works

  1. Claude Code submits a command with daleq_submit (or daleq submit from a shell) and gets a job id back at once.
  2. The daemon queues the job and starts a supervisor for it. The supervisor runs detached, so restarting or crashing the daemon never kills a job.
  3. The supervisor runs the command in its own process group under watchdogs: a wall-clock limit, a no-output limit, fail_on, and ready_on or a ready probe. A kill takes the whole process tree.
  4. Everything about the job lives in jobs/<id>/: job.json, status.json and output.log.
  5. The agent waits in bounded steps (daleq_wait blocks at most 120 s per call), or, with the plugin, is told by one line when the job ends or becomes ready. After a pause, the same submit attaches to the finished job instead of running it again.

The problem

Coding agents hang on long commands. A build, a test suite or a dev server ties up the session. A rate-limit pause or a crash loses the result. A process that never ends blocks the agent for good.

The usual answers are a background task that dies with the session, or a sleep loop that polls and burns turns.

What it does

  • MCP tools for Claude Code: daleq_submit, daleq_wait, daleq_status, daleq_logs (grep with context lines, time windows), daleq_cancel, daleq_list and daleq_fetch.
  • Watchdogs: a wall-clock limit (30 minutes by default), a no-output limit (10 minutes means hung), a regex that fails a job early, and a regex or a probe (a URL, a port, a command) that marks a server ready.
  • Results that survive: every job's output and outcome stay on disk for 7 days. Resubmitting the same command on an unchanged tree reuses the earlier result. reuse_on narrows "unchanged" to the files a result depends on.
  • A hook that turns away Bash and PowerShell commands that never end or only wait (tail -f, sleeps of a minute or more, polling loops). A plain dev server or watcher command (npm run dev) it starts as a daleq job itself.
  • Job events in the live session: with the plugin, the agent is told when a job it is not waiting for ends or becomes ready.
  • A verify gate, if the project asks for one: with [verify] tasks = ["test"] in .daleq.toml, Claude may not stop while one of those tasks fails.
  • A test guard, off until a project turns it on: the hook keeps an agent from editing, skipping or deleting the tests that were already there.
  • A CLI and a live panel for people: daleq submit --wait -- go test ./... and daleq top.
  • Device pools: iPhone, iPad and Apple Watch simulators, or your own list of devices, leased to jobs and healed before reuse.

The edge

  1. Durable results. A daleq job and its log outlive a session exit, a rate-limit pause and a crash.
  2. Watchdogs with no model in the loop. A job that prints nothing for 10 minutes is killed as hung. A regex or a probe decides that a job failed or a server is ready; no model is asked.
  3. Result reuse without a build graph. The same command on the same tree is not run twice, and nothing has to be declared first. Where you do declare, it is one list of globs.
  4. A hook that reads the command as a shell would. Quoted strings, heredoc bodies and comments are text, so a commit message that mentions sleep 5 passes.
  5. Guard rails for unattended work. The verify gate holds "done" until the project's own tasks pass, and the test guard keeps the existing tests read-only.

Device pools with healing and leases add one more for mobile work.

How it compares

Claude Code runs commands in the background by itself: Bash with run_in_background, the Monitor tool, and /tasks. That needs no install and is enough for a command that ends while you are in the session. daleq is for what it leaves out.

When not to use it

  • The command ends while the session is open and you are there to see it: a quick build, a dev server for the next ten minutes, a log to watch. Prefer the native tools.
  • You rely on Claude Code's Bash allow rules or sandbox. Commands sent through daleq are not checked by them.
  • Several agents only need one build at a time. block/agent-task-queue covers that with far less code.
  • Your tasks are already modelled in Turborepo, Nx or Bazel. Those hash inputs per task and restore output files.
  • You need several machines or Windows to be dependable. Both are experimental.
  • You use another agent and want it proven. Codex CLI, Cursor, GitHub Copilot and Gemini CLI use the same MCP server and CLI, but none of that setup is tested yet.

How far this release is tested. Job events, the hook's rewrite of dev servers, ready probes, reuse_on, log time windows, the verify gate and the test guard are new. They were checked on Linux only. There has been no real macOS or Windows run, and none in a live Claude Code session: monitor lines, the rewrite prompt and the Stop hook are untried there.

Compared on 2026-11-19 from each tool's public page. Other tools change; check before you choose.

Install

Not public yet. The repository is private today. These are the commands as they will be once it is public.

/plugin marketplace add mr-wheelkers/daleq
/plugin install daleq@daleq
/daleq-setup

/daleq-setup downloads the prebuilt daleq binary for your machine from the latest GitHub release, checks it against the release's checksums and installs it to ~/.local/bin. Then restart Claude Code so the MCP server starts.

The plugin brings the MCP server, the hooks, the skill, a monitor that reports job events (daleq watch), and /daleq-status. To prepare a project so that everyone who opens it in Claude Code uses daleq, run daleq init in its folder.

Quick start

Ask the agent in plain words; the skill and the hook steer it to daleq.

  • "Run the full test suite and tell me what failed." The agent submits it, waits in bounded steps, and reads the first failure lines daleq highlights.
  • "Start the dev server and check the home page loads." The agent submits it as an io job with ready_on: "listening on", waits until it is ready, checks the page, and cancels it when done.
  • "Build the release, I'll be back in an hour." After the break, the same submit attaches to the finished job instead of building again.
