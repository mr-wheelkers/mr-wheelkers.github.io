daleq

A small local daemon that runs long commands for a coding agent. It hands back a job id at once, runs the command under watchdogs, and keeps every output and outcome on disk.

How it works

  1. Claude Code submits a command with daleq_submit (or daleq submit from a shell) and gets a job id back at once.
  2. The daemon queues the job and starts a supervisor for it. The supervisor runs detached, so restarting or crashing the daemon never kills a job.
  3. The supervisor runs the command in its own process group under watchdogs: a wall-clock limit, a no-output limit, fail_on and ready_on. A kill takes the whole process tree.
  4. Everything about the job lives in jobs/<id>/: job.json, status.json and output.log.
  5. The agent waits in bounded steps (daleq_wait blocks at most 120 s per call) and reads the result. After a pause, the same submit attaches to the finished job instead of running it again.

The problem

Coding agents hang on long commands. A build, a test suite or a dev server ties up the session. A rate-limit pause or a crash loses the result. A process that never ends blocks the agent for good.

The usual answers are a background task that dies with the session, or a sleep loop that polls and burns turns.

What it does

  • MCP tools for Claude Code: daleq_submit, daleq_wait, daleq_status, daleq_logs (with grep), daleq_cancel, daleq_list and daleq_fetch.
  • Watchdogs: a wall-clock limit (30 minutes by default), a no-output limit (10 minutes means hung), a regex that fails a job early, and a regex that marks a server ready.
  • Results that survive: every job's output and outcome stay on disk for 7 days. Resubmitting the same command on an unchanged tree reuses the earlier result.
  • A hook that turns away Bash and PowerShell commands that never end or only wait (dev servers, tail -f, watch modes, polling loops) and points the agent to daleq.
  • A CLI and a live panel for people: daleq submit --wait -- go test ./... and daleq top.
  • Device pools: iPhone, iPad and Apple Watch simulators, or your own list of devices, leased to jobs and healed before reuse.
  • Several machines: one queue can span a Mac, a Linux box and a Windows PC over mutual TLS.

The edge

Four things were found nowhere else together.

  1. Durable results. A daleq job and its log outlive a session exit, a rate-limit pause and a crash.
  2. Watchdogs on silence and on output patterns. A job that prints nothing for 10 minutes is killed as hung; fail_on ends one early on a known fatal line.
  3. Result reuse without a build graph. The same command on the same tree is not run twice, and nothing has to be declared first.
  4. An enforcing hook that understands shell structure: quoted strings, heredoc bodies and comments are text, so a commit message that mentions sleep 5 passes.

Device pools with healing and leases add a fifth for mobile work.

How it compares

Running a command in the background and reading its logs later is no reason to install anything. Claude Code does that natively, with no install, and its background tasks obey your Bash permission rules and sandbox. They are cleaned up when Claude Code exits; that is where daleq differs.

When not to use it

  • You only need a background run inside one session. Use Claude Code's own background tasks.
  • Several agents only need one build at a time. block/agent-task-queue covers that with far less code.
  • You run declared, long-lived services. pitchfork and process-compose have ready checks by HTTP, TCP or command; daleq's is an output regex.
  • Your tasks are already modelled in Turborepo, Nx or Bazel. Those hash inputs per task and restore output files; daleq fingerprints the whole git tree.
  • You rely on Claude Code's Bash allow rules or sandbox. Commands sent through daleq are not checked by them: daleq refuses only what matches your Bash(…) deny rules.
  • You are on Windows and need it to be boring. Windows support is experimental.

The cluster layer (several machines, mutual TLS, snapshots) is a large surface for a tool with one maintainer. The single-machine daemon is the core.

Install

Not public yet. The repository is private today. These are the commands as they will be once it is public.

/plugin marketplace add mr-wheelkers/daleq
/plugin install daleq@daleq
/daleq-setup

/daleq-setup downloads the prebuilt daleq binary for your machine from the latest GitHub release, checks it against the release's checksums and installs it to ~/.local/bin. Then restart Claude Code so the MCP server starts.

To prepare a project so that everyone who opens it in Claude Code uses daleq, run daleq init in its folder.

Quick start

Ask the agent in plain words; the skill and the hook steer it to daleq.

  • "Run the full test suite and tell me what failed." The agent submits it, waits in bounded steps, and reads the first failure lines daleq highlights.
  • "Start the dev server and check the home page loads." The agent submits it as an io job with ready_on: "listening on", waits until it is ready, checks the page, and cancels it when done.
  • "Build the release, I'll be back in an hour." After the break, the same submit attaches to the finished job instead of building again.
